02 · The Problem

02线程为什么“贵”？

传统 Java 线程通常是对操作系统线程的一层封装。它可以像普通对象一样使用， 但创建、调度与维护堆栈都需要系统资源，因此数量不能无限增长。

服务端经常采用“一请求一线程”模型：请求进入，分配一条线程；业务代码顺序执行， 遇到数据库、网络或文件 I/O 时等待。这种写法直观、可调试，却会在并发量很大时被线程数量卡住。

01

平台线程

与底层操作系统线程绑定。适合数量相对稳定、长时间运行或需要稳定并行度的任务。

02

虚拟线程

由 JDK 提供的轻量线程。阻塞时通常可卸载，数量可以远大于操作系统线程。

03

载体线程

真正执行 Java 代码的平台线程。虚拟线程运行时挂载到载体，等待时可让出载体。

虚拟线程是 java.lang.Thread 的一种实现，但它不会在整个生命周期内独占操作系统线程。 JDK 的调度器把大量虚拟线程映射到少量载体线程上，形成 M:N 调度。

最容易理解错的一点：虚拟线程不是“执行更快的线程”。CPU 密集型任务增加线程数不会突破核心数量。它主要提升大量并发任务、且任务经常等待 I/O 时的吞吐量。

03 · Interactive Model

03把“挂载”和“卸载”看清楚

虚拟线程开始执行时，调度器把它挂载到一条载体线程上。遇到可卸载的阻塞操作后， 虚拟线程进入等待，载体被释放并继续运行其他虚拟线程。恢复条件满足后，它再回到调度队列。

在 JDK 21 中，虚拟线程调度器默认是一个 FIFO 模式的工作窃取 ForkJoinPool。载体数量默认等于可用处理器数； 它与 parallel stream 使用的 common pool 不是同一个池。

深入一步：调度器参数在哪里调？

可以通过系统属性 jdk.virtualThreadScheduler.parallelism 调整调度器并行度，通过 jdk.virtualThreadScheduler.maxPoolSize 设置载体池的上限。教学与默认业务场景通常无需调整；只有在有测量依据和明确瓶颈时才修改。

04 · JDK 21 API

04三种创建方式，优先选哪一种？

JEP 444 为 Thread 增加了虚拟线程创建 API，同时提供了与 ExecutorService 生态兼容的“一任务一线程”执行器。 课堂和实践都建议优先采用执行器写法，因为资源关闭与任务完成等待更清晰。

一任务一线程，并自动等待全部任务结束

适合服务端请求、批量 I/O 任务，通常是最容易迁移到虚拟线程的入口。

try (var executor =
         Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> doWork());
} // close() 自动调用，并等待任务结束

创建后立即启动一条虚拟线程

适合演示或独立后台任务；涉及多条任务时仍需自行管理生命周期。

Thread.startVirtualThread(() -> {
    System.out.println("running");
});

先配置名称，再启动

适合需要线程名称、未启动状态或从同一个 Builder 批量创建线程的场景。

Thread thread = Thread.ofVirtual()
        .name("order-worker")
        .start(() -> doWork());
对比项 平台线程 虚拟线程
资源关系 通常与操作系统线程一一绑定 按需挂载到载体线程，可大量存在
典型写法 线程池 + 固定并发度 每个任务新建一条虚拟线程
适合任务 CPU 密集、长期运行任务 大量阻塞等待的 I/O 密集任务
主要价值 复用昂贵的线程资源 提高可扩展并发数，通常改善吞吐量
05 · Hands-on

05第一个可运行示例

下面创建 100 个“模拟 I/O”任务，每条任务睡 300 毫秒。执行器会为每个提交的任务创建一条虚拟线程， try-with-resources 结束时会自动关闭执行器并等待任务完成。

VirtualThreadDemo.java 
import java.time.Duration;
import java.util.concurrent.Executors;
import java.util.stream.IntStream;

public class VirtualThreadDemo {
    public static void main(String[] args) {
        long start = System.nanoTime();

        try (var executor =
                 Executors.newVirtualThreadPerTaskExecutor()) {

            IntStream.rangeClosed(1, 100).forEach(id ->
                executor.submit(() -> {
                    // 模拟一次 I/O 等待
                    Thread.sleep(Duration.ofMillis(300));

                    Thread current = Thread.currentThread();
                    System.out.printf(
                        "任务 %03d | %s | virtual=%s%n",
                        id,
                        current.getName(),
                        current.isVirtual()
                    );
                    return id;
                })
            );
        }

        long elapsed = Duration.ofNanos(
            System.nanoTime() - start
        ).toMillis();
        System.out.printf("全部完成，用时约 %d ms%n", elapsed);
    }
}
预期输出（任务顺序可能不同）
任务 001 | virtual-1 | virtual=true
任务 002 | virtual-2 | virtual=true
...
任务 100 | virtual-100 | virtual=true
全部完成，用时约 300 ms

观察重点：100 个任务都睡了 300 ms，但总耗时并不等于 30,000 ms。它们并不是靠“跑得更快”完成，而是在等待期间把载体线程让了出来。

06 · Fit & Limits

06什么时候适合，什么时候不适合？

判断标准不是“是不是新 API”，而是任务在做什么。虚拟线程擅长扩大等待型任务的并发规模， 并不能让 CPU 计算本身变快。

适合：高并发、非 CPU 密集

  • 每个请求可以保留顺序、阻塞式代码
  • 任务大量等待网络、数据库或队列
  • 并发请求数量远大于 CPU 核心数量
  • 传统“线程池 + 回调/异步链”难以维护

不适合：用线程数提升计算速度

  • 长时间占满 CPU 的排序、加密、压缩任务
  • 希望用虚拟线程池限制下游并发度
  • 依赖固定线程的昂贵 ThreadLocal 资源
  • 频繁在 synchronized 中执行长时间阻塞 I/O

不要池化虚拟线程。官方文档明确建议一条虚拟线程只服务一个任务。虚拟线程本身很便宜，池化会再次引入共享、生命周期和 ThreadLocal 污染问题。如果要限制对下游资源的并发访问，请使用 Semaphore 等并发控制工具。

迁移时最常见的两个坑

01THREAD LOCAL

把 ThreadLocal 当成连接缓存

传统线程池会复用线程，因此有人把昂贵对象缓存在 ThreadLocal 中。虚拟线程通常一任务一条，照搬这种写法可能变成“每个任务创建一份昂贵资源”。

// 不要假设虚拟线程会被复用
static final ThreadLocal<Connection> CONNECTION =
        ThreadLocal.withInitial(this::openConnection);
02PINNING

JDK 21 中，注意 synchronized 固定载体

JEP 444 说明，虚拟线程在 synchronized 块或方法中执行阻塞操作时可能被固定到载体线程。频繁且长时间的固定会妨碍扩展。对高频、可能阻塞 I/O 的热点代码，可考虑 ReentrantLock。

// JDK 21：热点路径中谨慎使用
synchronized (lock) {
    remoteService.call(); // 可能阻塞
}

// 可改为
lock.lock();
try {
    remoteService.call();
} finally {
    lock.unlock();
}

版本提示：JDK 21 仍存在 synchronized 导致的固定载体问题。后续 JDK 版本通过 JEP 491 移除了这一限制，但本课程以 JDK 21 的行为为准，不能把更新版本的行为直接套回来。

07 · Observe

07在生产中如何观察与诊断？

虚拟线程仍然是 Thread 实例，但数量可能非常大。 JDK 21 提供了新的线程转储方式，让平台线程与虚拟线程分组展示；JFR 也能记录虚拟线程启动、结束和固定载体事件。

DIAGNOSTICS 
# 生成包含虚拟线程的新格式线程转储
jcmd <pid> Thread.dump_to_file -format=json threads.json

# 出现固定载体时输出简短栈信息
java -Djdk.tracePinnedThreads=short VirtualThreadDemo
观察目标 可用手段 关注点
线程状态 jcmd Thread.dump_to_file 虚拟线程是否长时间运行或等待
固定载体 JFR / -Djdk.tracePinnedThreads 阻塞时是否捕获了载体线程
资源缓存 代码审查 + 分配监控 是否把昂贵对象错误放入 ThreadLocal
吞吐变化 真实负载压测与 JFR 改善来自等待释放，而非单任务延迟

迁移策略：从小范围 I/O 请求链路开始，先确认任务类型，再替换执行器，随后压测吞吐、观察固定载体和 ThreadLocal 分配。不要为了“使用新特性”一次性替换全部线程模型。

09 · Summary

09本章小结

TAKEAWAYS

把“一个任务一条线程”重新变成可扩展的写法

  • 虚拟线程由 JDK 实现，通过 M:N 调度映射到少量载体线程。
  • 它的价值在吞吐量与编程模型，不在单任务执行速度。
  • 优先使用 Executors.newVirtualThreadPerTaskExecutor()。
  • 不要池化虚拟线程；需要限流时使用 Semaphore 等工具。
  • JDK 21 要警惕 synchronized 固定载体和 ThreadLocal 资源复制。
  • 用真实负载、线程转储、JFR 和固定载体诊断验证迁移效果。
