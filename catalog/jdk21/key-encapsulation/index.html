01 · CONCEPTUAL MODEL

01先抓住核心模型

KEM 用接收方公钥派生共享对称密钥，并生成可传输的封装密文。JDK 21 的 javax.crypto.KEM 为 RSA-KEM、DHKEM、未来后量子 KEM 等提供标准 API 形态。

ENCAPS

封装

发送方用接收方公钥生成共享密钥与封装密文。

DECAPS

解封装

接收方用私钥处理封装密文，得到同一共享密钥。

PROVIDER

算法提供者

KEM.getInstance 选择实现；支持和配置由 Security Provider 决定。

  • 新增 javax.crypto.KEM、Encapsulator、Decapsulator 等类型。
  • 共享密钥以 SecretKey 返回，允许实现返回不可提取的密钥。
  • 密钥对生成继续使用 KeyPairGenerator，而不是新增一套密钥生成 API。
02 · HANDS-ON

02读取 KEM 能力并创建封装器

示例保持最小可读，重点是展示这项能力如何使用，以及它与普通 Java 代码的关系。

KemDemo.java 
import java.security.KeyPairGenerator;
import java.security.PublicKey;
import javax.crypto.KEM;

public class KemDemo {
    public static void main(String[] args) throws Exception {
        var generator = KeyPairGenerator.getInstance("EC");
        var keyPair = generator.generateKeyPair();
        PublicKey receiverPublicKey = keyPair.getPublic();

        KEM kem = KEM.getInstance("DHKEM");
        KEM.Encapsulator encapsulator =
            kem.newEncapsulator(receiverPublicKey);

        KEM.Encapsulated result = encapsulator.encapsulate();
        System.out.println(result.key().getAlgorithm());
        System.out.println(result.encapsulation().length);
    }
}

算法支持由 Provider 决定：实际主题应通过 Security.getProviders() 或 getInstance 的异常结果确认当前运行时就绪情况。

不要自行拼接协议：共享密钥、封装密文、参数和高层握手消息都有明确格式，应遵循 KEM、HPKE 或 TLS 等协议规范。

03 · BOUNDARIES

03工程中的边界与易错点

能写出示例不代表可以安全迁移。下面两个问题最值得在设计和评审阶段确认。

01WATCH OUT

把封装密文当普通对称密文

KEM 密文用于恢复共享密钥，不应直接当作业务数据加密结果。

02WATCH OUT

混淆密钥对用途

公钥与私钥职责不同；发送方只需要接收方公钥，接收方私钥不应传输。

04 · SUMMARY

04本章小结

TAKEAWAYS

为标准 KEM 建立统一的封装、解封装接口。

  • KEM 用非对称公钥派生对称共享密钥。
  • 密钥对生成沿用既有 KeyPairGenerator。
  • 安全实现必须遵循协议，不应自创格式。
